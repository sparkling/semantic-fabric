01 / THE CHANGE

A daily harness, not another research programme.

Before this repair

A substantial closed-candidate experiment existed, but the programme’s normal native edit/test loop did not run through it.

  • Model policy in the ADR was not the daily execution contract.
  • The legacy experiment’s worktree launchers conflicted with the main-only rule.
  • Manual command evidence needed a consistent task-to-commit lifecycle.

What is now implemented

A project-specific delivery adapter uses the installed MetaHarness VerifierRegistry and the existing native executor.

  • One scoped task and one integration writer on main.
  • Explicit model/effort handoff, recorded commands, failure history and recovery.
  • Verification tied to unchanged evidence and the exact next scoped commit.

The old experiment is still separate and optional. This repair does not claim that its HarnessKernel or learned router drives the daily loop. No Darwin, GEPA, AVO, retrieval tuning, or new product architecture was enabled.

02 / THE DELIVERY PATH

From one requirement to one verified commit.

Task ownership and existing work

Declare the requirement, exact file scope, owner, thread, build command and acceptance commands. begin requires an explicit adoption list for already-dirty scoped files and records their starting hashes. Other dirty work must remain unchanged. Adoption is not verification.

finish requires the exact next single-parent main commit, only scoped changes, no outstanding scoped changes, and still-valid check evidence. The CLI itself never commits or pushes.

Checks, failures and interruption recovery

Checks run sequentially, without shell expansion. Source and selected build-environment hashes, exit status, elapsed time and private output hashes are recorded. Missing checks, changed source, changed logs, changed environment or failed commands invalidate the result. An empty verifier set is rejected.

Linux flock serializes operations. Explicit recovery checks the recorded nonce, PID/start identity and child process group. A live owner, surviving child or uncertain spawn window refuses recovery. Pause/resume retains history and requires a fresh native handoff.

Division of responsibility

Native Codex / Claude: authenticated execution, editing and scoped Git integration. Delivery adapter: task lifecycle, declared checks and commit-bound development evidence. Ruflo MCP: coordination, repository memory and result read-back.

A Ruflo worker record is not a native executor. The delivery CLI does not launch a second model host, and a native agent is not proof that a tracked Ruflo swarm exists.

03 / MODEL USE

Faster defaults. Explicit escalation.

The route is executable project policy, not a learned prediction of model quality. New supporting tasks start with the appropriate smaller model; the selected main model is retained. This is not a request to downgrade the main conversation.

Problems found during qualification — not hidden
  • Source inventories omitted 100 already-tracked Rust files and six PostgreSQL lifecycle files. The lists were repaired without editing that product code.
  • Historical replay projections included post-historical paths. Those paths were excluded; the original historical expected digests were preserved.
  • Current fingerprints changed legitimately with current manifests and were updated separately from historical anchors.
  • Packed-controller tests timed out under concurrent resource contention. Test-file concurrency was set to two; the final full suite passed without removing tests.
  • A build that regenerated tracked metadata exited zero but was correctly recorded as failed evidence because source changed. A stable follow-up build passed.

05 / CRITICAL REVIEW

What this harness does not prove.

Review the trust boundary before relying on the evidence
BoundaryCurrent realityReview implication
Cooperative enforcementCanonical instructions require use of the harness. A person or tool can still bypass the CLI.It is a development workflow, not an OS security sandbox.
Native identityModel/effort observations are supplied by the trusted host or operator.A matching handoff is not cryptographic provider attestation.
Acceptance qualityThe owner selects commands and test cases.A zero exit code or empty test selection cannot prove the requirement was tested.
Evidence authenticityLocal hashes detect accidental change and stale evidence.They do not establish independent authorship or a tamper-proof release authority.
Build accessSelected environment variables are retained; trusted scripts still have normal filesystem access.Filtering provider variables is not credential isolation.
Platform and recoveryOperation exclusion uses Linux flock and /proc. Ambiguous spawn recovery refuses to proceed.Windows/macOS behavior is not qualified by this repair. Some hard crashes require operator investigation.
ParallelismOne integration writer and sequential declared checks per delivery task.Read-only native support can be parallel; shared writes and competing build processes are not enabled.
Product completionThe floating-pool application patch is still uncommitted and unverified.Harness completion is not application completion, release readiness or permission to resume.

Process-safety limits default to 30 minutes and 10 MB of combined output per check. Explicit overrides allow up to 24 hours / 100 MB. These limit individual build processes; they are not model or subscription budgets.
