Architecture decision · 27 July 2026

Issue #6 under hostile review

An adversarial assessment of the proposed semantic-fabric ↔ Oxigraph Nova integration, tested against both repositories’ current code rather than the issue’s stated API shapes.

Decision No-go as written Conditional go for a consumer-led, two-seam pilot.

Do not implement issue #6 as a bundle, expose raw planner internals, make SqlBackend object-safe, or publish the existing generic block_on. The collaboration is promising, but its proposed seams contain correctness and runtime traps.

Ask Nova to prove one SQLite materialization vertical slice first. In parallel, accept only generally useful upstream changes: a fallible quad sink and, if the slice demonstrates the need, a redacting SourceSpec parser. Design live virtualization separately around an opaque quad-pattern API.

The honest balance

The proposal identifies real reuse opportunities and offers downstream implementation capacity. Its risk comes from treating convenient internal seams as stable integration contracts before the consumer has built a working vertical slice.

Why say yes

  • Places semantic-fabric’s mapping and SQL engine behind a second, materially different product surface.
  • Creates a credible native + virtual graph story without duplicating R2RML, SQL dialect, datatype, and term-generation logic.
  • Nova volunteers ownership of its adapter, federation, CLI/server wiring, and upstream seam PRs.
  • A fallible streaming sink and a safe source-spec parser are useful beyond Nova.
  • Both projects already share the same Oxigraph RDF/SPARQL crate versions, reducing type-conversion friction.
  • Materialization can validate the partnership before committing to live query integration.

Why say no

  • The proposed sync/object-safe boundary conflicts with semantic-fabric’s async, mutable, cursor-borrowing execution model.
  • The requested raw Branch exposure drops hidden correctness metadata and bypasses planner invariants.
  • A fallible push sink alone does not bridge Nova’s synchronous pull-based bulk_load_boxed.
  • Graph selectors are absent from the suggested triple-pattern API; applying limit = 1 before graph filtering can return false negatives.
  • The source-string opener freezes server policy, can leak credentials in errors, and currently hard-codes PostgreSQL NoTls.
  • Nova main does not yet contain the described FederatedDataset or R2RML adapter; neither repository has a release or tag, and semantic-fabric crates remain version 0.0.0.

Six ways the current plan breaks

The “runtime-free bridge” is not generic

exec_core::block_on polls with a no-op waker in a tight loop. Its own comment limits it to always-ready futures. PostgreSQL, MySQL, and the owned SQLite channel adapter may return Pending; publishing this as a generic sync wrapper risks an infinite busy-spin.

Vec<Branch> is not a complete plan

ADR-0034 added dedup_groups and construct_drops_some_branch_var. These values are captured during translation and cannot always be reconstructed from finished branches. Raw pattern branches also bypass D2 pooling/dedup. A constructor that fills “common defaults” can create a compiling, executable, wrong-answer plan.

The graph dimension disappears

Nova’s contract has five graph selectors. The proposed input is only a spargebra TriplePattern. semantic-fabric’s unfolding behavior depends on an internal graph context; a fresh unfolder defaults to the default graph. Post-filtering is not enough when limit = 1 is pushed before that filter.

Type erasure is framed at the wrong layer

Nova can box a concrete R2rmlDataset<B> as Box<dyn Dataset>; SqlBackend itself need not become object-safe. The hard problem is safely turning an async borrowed cursor into a lazy sync iterator—not choosing between a dyn backend and a generic federator.

Push-to-pull needs a bounded bridge

semantic-fabric pushes quads asynchronously into a callback. Nova bulk loading synchronously pulls from an iterator. Clean cancellation and sink-error propagation require a bounded channel, an owning worker, and join/error semantics. A fallible callback is useful, but insufficient by itself.

The public opener would expose policy and secrets

Current errors interpolate the full PostgreSQL conninfo or unrecognized source string, potentially including passwords. The helper also chooses pool behavior and NoTls. Parsing may belong in sf-sql; opening belongs in a caller-controlled integration layer with redaction and configurable TLS.

Adversarial bottom line: the issue’s strongest claim is “the internals already do almost everything.” That is also its most dangerous assumption. The remaining gaps sit exactly at ownership, scheduling, graph semantics, cancellation, and correctness metadata boundaries—the expensive boundaries.

Decision gates

Proceed when

  • Nova provides a working consumer branch, not only upstream API requests.
  • The bridge is bounded, cancellable, and propagates both producer and storage errors.
  • Graph filtering happens before existence limits, with all selectors tested.
  • No downstream code can instantiate incomplete semantic-fabric plans.
  • Credentials are redacted and PostgreSQL TLS is configurable.

Stop when

  • The sync adapter requires generic busy-polling or blocks a Tokio worker.
  • A single mutex serializes all live virtual queries with no bounded queue policy.
  • The only route forward is exposing raw Branch/Plan internals.
  • Graph correctness is deferred behind a “filter later” shortcut.
  • Upstream maintenance cost arrives before a Nova vertical slice does.
